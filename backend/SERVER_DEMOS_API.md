# Загрузка демо с сервера CS2

Задайте секрет `CS2_DEMO_API_KEY` в корневом `.env` для Docker Compose
или в `backend/.env` для запуска Node напрямую. Используйте случайный длинный
ключ, например результат `openssl rand -hex 32`. После изменения переменной
пересоздайте backend: `docker compose up -d --build backend`.
Без ключа эндпоинт возвращает 503. Ключ хранится только на backend и игровом сервере.

`POST /api/server/demos`, заголовок `Authorization: Bearer <ключ>`.
Тело `multipart/form-data`:

- `demo`: один непустой файл с расширением `.dem`, максимум 2 ГиБ.
- `tournament_id`: UUID существующего турнира (из URL турнира в админке).

Пример для Linux-сервера CS2:

```bash
curl --fail-with-body 'https://riftpc.ru/api/server/demos' \
  -H "Authorization: Bearer $CS2_DEMO_API_KEY" \
  -F 'demo=@/path/to/match.dem' \
  -F 'tournament_id=12345678-1234-1234-1234-123456789abc'
```

Отправляйте файл после завершения записи демо. Каждый успешный запрос создаёт
новый матч в указанном турнире; повторная отправка создаст ещё один матч.
Эндпоинт не выбирает уже существующий матч. Карта, составы и статистика
заполняются существующим парсером. Этап турнира назначается в админке.

Ответ 202 означает, что файл сохранён и запущена фоновая обработка.
`data.id` — ID демо, `data.match_id` — ID созданного матча,
`data.tournament_id` — ID турнира, `data.status` — `parsing`.
Проверять результат: `GET /api/demos/<data.id>`; итоговый статус — `parsed`
или `error` (причина в `error_message`). При ошибке парсинга файл сохраняется.
Фоновая обработка работает в процессе backend: перезапуск может её прервать.

Ошибки: 400 — некорректные поля/файл, 401 — неверный ключ, 404 — нет турнира,
413 — файл больше лимита, 500 — ошибка сохранения, 503 — ключ не настроен.
Фактическое содержимое демо проверяется парсером после ответа 202.
